# World data & C++ types

This plugin loads a **world** — a set of characters plus the context that makes them
talk in character. This page documents the on-disk shape of that data (the export
JSON the offline mode reads) and, for contributors, how the plugin's C++ types map
back to their schemas.

## World export JSON

In offline mode the plugin reads world data in the shape produced by
`GET /api/conversation/export/{worldId}`:

```json
{
  "worldName": "My World",
  "worldId": "my-world-id",
  "characters": [
    {
      "characterId": "npc_001",
      "firstName": "Elena",
      "lastName": "Torres",
      "gender": "female",
      "occupation": "Merchant",
      "birthYear": 1988,
      "isAlive": true,
      "openness": 0.7,
      "conscientiousness": 0.8,
      "extroversion": 0.9,
      "agreeableness": 0.7,
      "neuroticism": 0.2
    }
  ],
  "dialogueContexts": [
    {
      "characterId": "npc_001",
      "characterName": "Elena Torres",
      "systemPrompt": "You are Elena Torres, a merchant...",
      "greeting": "Hello! See anything you like?",
      "voice": "Kore",
      "truths": [
        { "title": "Craft", "content": "Elena makes handmade jewelry." }
      ]
    }
  ]
}
```

- **`characters`** provides data for the spawner and character mapping.
- **`dialogueContexts`** provides the pre-built prompts (personality, relationships,
  knowledge) the offline provider feeds to the local LLM. In **server mode** the
  server builds these prompts dynamically, so the export is only needed offline.

Export a world with:

```bash
curl http://localhost:8080/api/conversation/export/YOUR_WORLD_ID \
  > Content/InsimulData/world_export.json
```

`FInsimulWorldExportLoader` reads it (single-file or split-file layout) into
`FInsimulExportedWorld`.

## C++ type provenance (for contributors)

The plugin's C++ types fall into three tiers. **Only the *generated* tier is derived
from the canonical `@insimul/core` JSON Schemas** — the rest are hand-maintained and
stay that way.

| Tier | Files | Source of truth | Editable? |
| --- | --- | --- | --- |
| **Generated** | `Source/InsimulRuntime/Generated/InsimulGenerated.h` — plain `Insimul::Generated` structs (`SaveFile`, `SaveFileEnvelope`, `WorldIr` + nested) with `from_json` / `to_json` | `packages/core/schemas/{save-file,save-envelope,world-ir}.schema.json` | **No** — regenerated by codegen, drift-guarded |
| **Hand-written (SDK)** | `Source/InsimulRuntime/Public/InsimulTypes.h` (the reflected `FInsimul*` UStructs Blueprints bind to), `InsimulWorldExport.h` (the distilled `FInsimulExportedWorld` offline-export shape), and the plugin runtime (components / actors / widgets / subsystems / networking) | Hand-maintained (engine-facing / proto-derived) | **Yes** |
| **Template-legacy** | `templates/source/data/*.h` — parallel re-declarations (`CharacterData.h`, `QuestData.h`, `SettlementData.h`, …) vendored into exported games | Hand-maintained (drift-prone) | Being retired |

**The UStruct boundary.** The generated plain structs are the wire/DTO layer — a
faithful 1:1 image of the JSON schemas that (de)serializes via `nlohmann::json` and
carries **no** Unreal reflection macros, so it compiles and drift-checks without the
Unreal toolchain. The hand-written `FInsimul*` UStructs in `InsimulTypes.h` are what
Blueprints and the rest of the plugin bind to; they **convert at the boundary** —
parse JSON into the generated structs, then copy field-by-field into the reflected
types (and back out on save). Keeping the layers separate lets the DTOs regenerate
freely on a schema change without disturbing the reflected types. See
`Source/InsimulRuntime/Generated/README.md` for the full convention.

**Why the offline export stays hand-written.** `FInsimulExportedWorld` is the
*distilled* offline export (`GET /api/conversation/export/{worldId}` →
`world_export.json`) — a flattened dialogue-context shape, **not** the full
`WorldIr` — so it is not a duplicate of any generated DTO and stays hand-maintained.
New save/load or World-IR code should convert through `Insimul::Generated` at the
boundary.
